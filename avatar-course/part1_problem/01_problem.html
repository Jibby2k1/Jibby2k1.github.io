From one video to a drivable avatar#

What you will learn

  1. What the input and the output of the problem are, and what “drivable” means precisely.

  2. Why replaying or looking up video frames is not an avatar, shown by a baseline that fails.

  3. Which pieces a drivable avatar needs, and where each one is built in this course.

Prerequisites: Lesson 0.

1. The input: one camera, one person#

Someone stands in front of a single camera and turns around slowly. That is the whole capture. There are no markers, no depth sensor and no second view. Here is the toy version of that video: 16 frames of one full turn.

actor = cu.ToyActor()
cam = cu.orbit_camera(0, size=64)
turn_poses, turn_trans = cu.motion("turn", 16)
video = cu.make_video(actor, turn_poses, turn_trans, cam)
cu.show_images([video.frame(t) for t in range(0, 16, 2)], [f"frame {t}" for t in range(0, 16, 2)], size=1.5);

A video is a list of images \(I_1, \dots, I_T\). Each image is a 2D projection of a 3D person in some body pose \(\theta_t\). The camera never moves, but the person turns, so the camera sees every side. A turn in place gives the same pictures as a camera that circles a person who stands still. This is why one camera can be enough.

2. The output: a function, not a recording#

We want a model \(A\) that takes a body pose \(\theta\) and a camera \(c\) and returns an image:

\[ \hat I = A(\theta, c). \]

The model is drivable if this works for poses the capture never contained. A new pose can come from anywhere: another video, a motion-capture file, a keyboard. Three abilities are worth separating.

Ability

Question it answers

Enough for an avatar?

Replay

What did frame \(t\) look like?

No: that is the video.

New view

What does the frozen person look like from another side?

No: the person cannot move.

New pose

What does the person look like in a pose nobody recorded?

Yes.

3. A baseline that fails: look up the nearest frame#

Before building anything, try the laziest idea. To show the person in a new pose, find the training frame whose pose is closest and return it.

def pose_distance(a, b):
    """Mean rotation difference between two poses, in degrees (root joint included)."""
    Ra, Rb = cu.axis_angle_to_matrix(a), cu.axis_angle_to_matrix(b)
    cos = ((Ra.transpose(-1, -2) @ Rb).diagonal(dim1=-2, dim2=-1).sum(-1) - 1) / 2
    return torch.rad2deg(torch.acos(cos.clamp(-1, 1))).mean()

def nearest_frame(pose):
    d = torch.stack([pose_distance(pose, p) for p in video.poses])
    return int(d.argmin())

# a motion the capture never contained
new_poses, new_trans = cu.motion("dance", 8)
truth = cu.make_video(actor, new_poses, new_trans, cam)
lookup = torch.stack([video.frame(nearest_frame(p)) for p in new_poses])
cu.show_images([truth.frame(t) for t in (0, 2, 4, 6)] + [lookup[t] for t in (0, 2, 4, 6)],
               [f"wanted, frame {t}" for t in (0, 2, 4, 6)] + ["nearest training frame"] * 4, ncols=4, size=1.8);

The lookup can only return what was filmed. The capture has no raised arms and no bent knees, so the answer is wrong wherever the new pose differs from the turn. More footage does not fix this in general, because the number of poses a body can take grows much faster than any capture can cover.

lookup_psnr = np.mean([cu.psnr(lookup[t], truth.frame(t)) for t in range(len(truth))])
print(f"nearest-frame lookup on the new motion: {lookup_psnr:.1f} dB")

nearest-frame lookup on the new motion: 17.1 dB

PSNR, the peak signal-to-noise ratio, measures how close two images are. For images in \([0, 1]\) it is \(-10 \log_{10}\) of the mean squared error, in decibels (dB). Higher is better, and 3 dB is a factor of two in squared error. Part 8 looks at when PSNR can be trusted.

4. The same test with a drivable model#

Now use the model this course builds. For this lesson it is a black box: cu.ShellAvatar is the model and cu.fit trains it on the turn video. The next four parts open the box.

avatar = cu.ShellAvatar()
history = cu.fit(avatar, video, iters=220, seed=0)
print(f"fitted {avatar.n_gaussians} Gaussians in {history['seconds']:.0f} s")

driven = cu.render_video(avatar, truth)[0]            # the avatar in the new poses
cu.show_images([truth.frame(t) for t in (0, 2, 4, 6)] + [driven[t] for t in (0, 2, 4, 6)],
               [f"wanted, frame {t}" for t in (0, 2, 4, 6)] + ["avatar (pose never filmed)"] * 4,
               ncols=4, size=1.8);

fitted 9308 Gaussians in 4 s

avatar_psnr = cu.evaluate(avatar, truth)["mean_psnr"]
print(f"nearest-frame lookup: {lookup_psnr:.1f} dB    drivable avatar: {avatar_psnr:.1f} dB")
assert avatar_psnr > lookup_psnr + 3, "the avatar should beat the lookup clearly on unseen poses"

nearest-frame lookup: 17.1 dB    drivable avatar: 34.9 dB

The avatar was trained on a turn with the arms held still. It can raise them anyway. The reason is that it does not store pictures. It stores the person’s surface once, attached to a skeleton, and it knows how the skeleton moves the surface.

The avatar is also a 3D object, so the camera is free. The dance from a high three-quarter view:

side_cam = cu.orbit_camera(azimuth_deg=55, elevation_deg=25, size=128)
with torch.no_grad():
    frames = [avatar.render(side_cam, new_poses[t], new_trans[t])[0] for t in (0, 2, 4, 6)]
cu.show_images(frames, [f"new pose {t}, new camera" for t in (0, 2, 4, 6)], size=2.0);

  1. A renderer you can differentiate. The picture is a smooth function of the model’s numbers, so the error against the video can be turned into gradients. Part 2 builds it from Gaussians.

  2. A body that moves. A skeleton, and a rule for how the surface follows it. Part 3.

  3. A representation tied to the body. The appearance is stored on shells around the body surface, so it moves with the body and can also sit a little away from it, as clothes do. Part 4.

  4. Registration. For every frame the fit must know the pose and the camera. In this lesson the poses were exact, because the toy gives them away. A real pipeline estimates them, and its errors are the main reason real avatars are blurry. Part 5 shows this on the toy.

The remaining parts are about doing it well: small parts such as faces and hands (Part 6), motion that respects the floor (Part 7), measuring without fooling yourself (Part 8) and making it fast without changing the answer (Part 9).

6. What the toy leaves out#

The toy keeps the structure of the problem and removes what cannot be shipped or run on a laptop CPU. Keep the differences in mind.

In this course

In the real pipeline

A body of 17 capsules with a hand-written skeleton

SMPL, a body model learned from thousands of scans [Loper et al., 2015]

The true pose of every frame is known

Poses come from trackers and are wrong by a few degrees or millimetres

A perfect mask from the renderer

Masks from a segmentation model

64-pixel frames, about 9,000 Gaussians

4K frames, about 100,000 Gaussians or more

The “person” is itself made of Gaussians

A real person: hair, skin, cloth that swings, changing light

The last row matters most. The toy person can be fitted almost perfectly, because the model and the truth are made of the same thing. A real capture cannot. Wherever a lesson shows a clean result on the toy, the matching “In the real pipeline” section says how far the real system gets.

From the real system#

Everything in this lesson so far used the toy actor. The clips below come from the real pipeline, run on the author’s own capture.

The result. A 360° turntable of the author’s hi-fi avatar (left) next to the previous model of the same person from an earlier capture session (right), in the same rest pose and camera. This is raw renderer output: no grading, floor or shadow. Notice that the avatar holds together from every side, including the back, which no single frame of the capture shows together with the front.

The chain on one frame. One training frame from the slow turn of the capture: the captured frame, the person mask from SAM 2, the body mesh tracked by GVHMR, and the fitted avatar rendered in that frame’s pose and camera. Notice that the tracked mesh is only roughly aligned with the person and has no clothes or hair. The pipeline refines the pose per frame from silhouettes and keypoints, and the Gaussians on the shells supply everything the mesh lacks. The standard track fits at 512 px, which is why the render is softer than the 4K frame.

The method behind each step is in the repository’s README.

Summary#

  • The input is one video of one person. The output is a function from a pose and a camera to an image.

  • “Drivable” means the function works for poses that were never recorded. Looking up recorded frames fails that test by construction.

  • A drivable avatar stores the surface once, tied to a skeleton, and renders it with a differentiable renderer so it can be fitted to the video by gradient descent.

  • The fit needs the pose of every frame. On the toy it is given; in practice it is the hardest input to get right.

Exercises#

  1. Drive the avatar with cu.motion("squat", 8) and compare with the actor. Which body region has the largest error, and why would a turn with straight legs leave it under-constrained?

  2. Make the lookup baseline as strong as you can: give it a capture that contains the dance itself, then test on wave. Does more footage of one motion help with another?

  3. The turn has 16 frames. Refit with only 4 of them (video.subset([0, 4, 8, 12])). What changes in the new poses?

Solution 1

poses, trans = cu.motion("squat", 8)
squat = cu.make_video(actor, poses, trans, cam)
out = cu.render_video(avatar, squat)[0]
err = [(out[t] - squat.frame(t)).abs().mean(-1) for t in (0, 2, 4)]
cu.show_images(err, ["error"] * 3, vmax=0.5)

The error gathers at the knees and the back of the thighs. In the turn the legs are straight, so the skin around the knee was only ever seen in one configuration, and the inner sides of the legs were partly hidden.

Solution 3

few = cu.ShellAvatar()
cu.fit(few, video.subset([0, 4, 8, 12]), iters=220)
print(cu.evaluate(few, truth)["mean_psnr"], "dB with 4 views;", avatar_psnr, "dB with 16")

Four views still cover front, back and both sides, so the result is close. The surfaces seen only at grazing angles (the sides of the arms and legs) get worse first.
